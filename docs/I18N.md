# i18n Sözleşmesi

Bu belge Konform'un dil mimarisini tanımlar. **Kod yazmadan önce okunması zorunlu.**
Buradaki en kritik kural şu: bu eklentide "dil" tek bir şey değil, **üç ayrı
eksendir** ve bunları birbirine karıştırmak en pahalı hatadır.

---

## 0. Kaynak dil İngilizce'dir

Kod içindeki **tüm kullanıcıya görünen dizgeler İngilizce yazılır.** Türkçe dahil
hiçbir dil kaynak dil olamaz.

Gerekçe teknik, tercih değil: translate.wordpress.org (GlotPress) kaynak dilin
`en_US` olduğunu varsayar. Kaynak Türkçe olursa Fransız bir çevirmen Türkçeden
Fransızcaya çeviri yapmak zorunda kalır — pratikte kimse yapmaz ve eklenti
Türkçe dışında hiçbir dilde kullanılamaz. "Tüm dünyada satılmalı" hedefiyle
doğrudan çelişir.

| Ne | Dil |
|---|---|
| `__()`, `_e()`, `_n()`, `_x()` içindeki dizgeler | **İngilizce** |
| `translators:` yorumları | **İngilizce** (çevirmenler okur) |
| Eklenti başlığı ve açıklaması (`Plugin Name`, `Description`) | **İngilizce** |
| `readme.txt` | **İngilizce** |
| Kod yorumları ve docblock'lar | Türkçe serbest (kullanıcıya gitmez) |
| Bu depodaki `docs/` belgeleri | Türkçe serbest |

Türkçe, diğerleri gibi bir **hedef** dildir: `languages/konform-tr_TR.po`.

## 1. Üç eksen

| Eksen | Ne belirler | Kim okur | Kaynak |
|---|---|---|---|
| **UI dili** | Yönetici ekranlarının dili | Mağaza sahibi | `get_user_locale()` |
| **Belge dili** | Faturanın üzerindeki metinlerin dili | **Alıcı** | Sipariş → alıcı ülkesi → mağaza varsayılanı |
| **Regülasyon profili** | Hangi ülkenin kural seti uygulanacak | Vergi idaresi | **Satıcının** ülkesi (mağaza adresi) |

Bu üçü **birbirinden bağımsızdır**. Somut örnek:

> İstanbul'daki bir mağaza, yönetim panelini Türkçe kullanıyor, Fransa'daki bir
> müşteriye satış yapıyor ve Alman iştiraki üzerinden fatura kesiyor.
>
> - UI dili → `tr_TR`
> - Belge dili → `fr_FR`
> - Regülasyon profili → `DE` (XRechnung)

Tek bir `get_locale()` çağrısıyla üçünü birden çözmeye çalışan her kod yanlıştır.

## 2. Belge dili, admin dilinden asla miras almaz

Fatura PDF'i ve e-postası **alıcının** dilinde üretilir. WordPress'in aktif
locale'i o sırada yöneticinin dilidir — doğrudan kullanılamaz.

Çözüm `switch_to_locale()` / `restore_previous_locale()` çifti. WooCommerce müşteri
e-postalarında aynı şeyi yapar; biz de aynı deseni izleriz:

```php
Locale::render( $documentLocale, static function () use ( $order ) {
    return $renderer->invoice( $order );
} );
```

`Locale::render()` dışında **hiçbir yerde** `switch_to_locale()` çağrılmaz.
Restore'u unutmak, yönetici panelini rastgele bir dilde bırakır.

### Belge dili çözümleme sırası

1. Sipariş meta `_konform_document_locale` (elle geçersiz kılma)
2. WPML / Polylang sipariş dili (`wpml_language` meta)
3. Sipariş oluşturulurken kaydedilen `wp_locale` meta
4. Fatura ülkesinden (`billing_country`) türetilen varsayılan locale
5. Mağaza varsayılanı (`get_locale()`)

Sipariş oluşturulduğu anda o anki locale mutlaka meta olarak yazılır — sonradan
geriye dönük doğru dili tahmin etmek mümkün değildir.

## 3. Kod listeleri çevrilmez

EN 16931 kod listeleri **kanonik**tir. Bunlar veri, metin değil:

| Liste | Örnek | Çevrilir mi |
|---|---|---|
| Vergi kategorisi (UNTDID 5305) | `S`, `Z`, `E`, `AE`, `K`, `G`, `O` | ❌ Asla |
| Para birimi (ISO 4217) | `EUR`, `TRY`, `PLN` | ❌ Asla |
| Ülke (ISO 3166-1 alpha-2) | `FR`, `DE`, `PL` | ❌ Asla |
| Birim (UN/ECE Rec 20) | `C62`, `KGM`, `LTR` | ❌ Asla |
| Belge tipi (UNTDID 1001) | `380`, `381`, `384` | ❌ Asla |

XML'e **daima kanonik kod** yazılır. Çevrilen şey yalnızca bu kodların yönetici
arayüzündeki **etiketidir**:

```php
// XML'e giden: her zaman 'AE'
$taxCategoryCode = 'AE';

// Ekranda görünen: kullanıcının diline göre
CodeList::label( 'tax_category', 'AE' ); // "Tersine tabi (reverse charge)"
```

Aynı kural sayı ve tarih biçimleri için de geçerlidir: **XML içinde** ondalık
ayırıcı her zaman `.` ve tarih her zaman `YYYY-MM-DD`'dir; locale biçimlendirmesi
yalnızca insan tarafından okunan PDF katmanında uygulanır.

## 4. Metin alanı (text domain)

- Metin alanı: **`konform`**
- Dizin: `/languages`

⚠️ WordPress.org, translate.wordpress.org'un çalışması için **metin alanının
eklenti slug'ına birebir eşit olmasını** şart koşar. Yani `.org` gönderiminden
önce slug kilitlenmeli; sonradan değiştirmek tüm kod tabanında arama-değiştirme
ve mevcut çevirilerin kaybı demektir.

**Karar (kilitli):** slug = metin alanı = `konform`.
Eklenti başlığı SEO'yu taşır: *"Konform – EU E-Invoicing for WooCommerce"*.

### Ücretsiz ve Pro ayrımı

| | Çeviri kaynağı |
|---|---|
| Ücretsiz (.org) | translate.wordpress.org — **kendi `.mo` dosyamızı göndermeyiz** |
| Pro (Freemius) | Kendi `.mo` dosyalarımız, `load_plugin_textdomain()` ile yüklenir |

Bu yüzden `languages/` dizininde ücretsiz sürümde yalnızca `.pot` bulunur.

## 5. Kodlama kuralları

```php
// ✅ Doğru — çıktı kaçışı ile birlikte
esc_html__( 'Ön uçuş kontrolü', 'konform' );
esc_attr__( 'Faturayı indir', 'konform' );

// ✅ Çoğul
sprintf(
    /* translators: %s: sipariş sayısı. */
    _n( '%s sipariş reddedilirdi.', '%s sipariş reddedilirdi.', $count, 'konform' ),
    number_format_i18n( $count )
);

// ✅ Belirsiz kısa metinlerde bağlam
_x( 'Kes', 'fatura kesme eylemi', 'konform' );

// ❌ Yanlış — değişken metin alanı, WP-CLI tarama yapamaz
__( $string, $domain );

// ❌ Yanlış — cümleyi parçalamak, çevrilemez dilbilgisi üretir
__( 'Toplam', 'konform' ) . ' ' . $count . ' ' . __( 'sipariş', 'konform' );
```

Ek kurallar:

- Her `%s` / `%d` içeren dizgenin üstüne `/* translators: */` yorumu **zorunlu**.
- Birden fazla yer tutucu varsa **daima numaralı** kullan: `%1$s`, `%2$s`.
  Kelime sırası dilden dile değişir.
- Sayılar `number_format_i18n()`, tarihler `wp_date()` ile biçimlenir — asla
  `date()` veya `number_format()` ile değil.
- Kullanıcıya görünen hiçbir dizge kod içinde sabit bırakılmaz; log ve XML
  içerikleri ise **çevrilmez** (makine okur).

## 6. Hata mesajları

Ön uçuş kontrolünün hata mesajları ürünün en önemli metinleridir — destek
talebinin yerine geçmeleri gerekir (bkz. SPEC.md, risk: destek yükü).

Şablon: **ne oldu → neden → nerede düzeltilir**

```
❌ "Geçersiz sipariş."
✅ "1042 numaralı siparişte alıcının KDV numarası eksik. Fransa'ya B2B satışta
    bu alan zorunlu. Sipariş > Fatura adresi bölümünden ekleyin."
```

Bu metinler uzundur ve çevrilmeleri pahalıdır — bu yüzden **kısa tutmak yerine
doğru tutmak** önceliklidir.

## 7. RTL

Yönetici arayüzü Arapça ve İbranice locale'lerde sağdan sola akar. CSS'te fiziksel
değil **mantıksal** özellikler kullanılır:

```css
/* ✅ */ margin-inline-start: 12px;  padding-inline: 16px;  text-align: start;
/* ❌ */ margin-left: 12px;          padding-right: 16px;   text-align: left;
```

Böylece ayrı bir `-rtl.css` üretmeye gerek kalmaz.

## 8. Araçlar

```bash
# .pot üret (eksik translators yorumlarını da uyarır)
docker compose run --rm wpcli i18n make-pot \
  wp-content/plugins/konform \
  wp-content/plugins/konform/languages/konform.pot \
  --slug=konform --domain=konform

# .po dosyalarını .mo ve .l10n.php'ye derle (Pro sürüm için)
docker compose run --rm wpcli i18n make-mo wp-content/plugins/konform/languages
docker compose run --rm wpcli i18n make-php wp-content/plugins/konform/languages
```

`make-php` çıktısı WP 6.5+ tarafından `.mo`'dan daha hızlı okunur; Pro sürümde
ikisi de gönderilir.

## 9. Eklenti çevirileri ayrı gelir — çözüldü

`Locale::installed()` eksik bir dil paketini talep anında indirir ve bu doğrulandı
— `fr_FR` kurulu değilken çağrıldığında indirilip geçiş yapılıyor.

**Ancak `wp_download_language_pack()` yalnızca WordPress ÇEKİRDEK çevirilerini
indirir.** Eklenti çevirileri (bizimkiler ve WooCommerce'inkiler) ayrı paketlerdir.
Canlı doğrulama bunu gösterdi:

```
Locale::render( "fr_FR", fn() => __( "Billing address", "woocommerce" ) )
  -> "Billing address"      // cevrilmedi: WooCommerce fr_FR paketi kurulu degil
```

Sonuç: çekirdek dizgeler doğru dile geçer, eklenti dizgeleri geçmez.

### Etkisi sürüme göre

| Sürüm | Bizim dizgelerimiz | Durum |
|---|---|---|
| Pro (Freemius) | `.mo` dosyaları eklentiyle birlikte gelir | ✅ Sorun yok |
| Ücretsiz (.org) | translate.wordpress.org'dan ayrıca inmeli | ⚠️ Eksik |

### Çözüm

`Locale::ensure_plugin_translations()` eklenti paketlerini de indirir.

İki incelik vardı:

1. **Çekirdek paketi kurulu olsa bile eklenti paketleri eksik olabilir.** İlk
   deneme yalnızca çekirdek paketi indirilirken tetikleniyordu; locale zaten
   kuruluysa hızlı yoldan dönülüyor ve eklenti çevirileri hiç denenmiyordu.
   Artık iki konu ayrı ele alınıyor.

2. **WordPress bekleyen çeviri güncellemelerini yalnızca SİTENİN dilleri için
   listeler.** Hedef locale `plugins_update_check_locales` kancasıyla geçici
   olarak eklenmezse `wp_get_translation_updates()` boş döner.

Sonuç bir gün hatırlanır; her fatura üretiminde güncelleme kontrolü yapmak
kabul edilemez bir maliyet olurdu.

Doğrulandı:

```
de_DE : Rechnungsadresse
fr_FR : Adresse de facturation
nl_NL : Factuuradres
```

## 10. Kabul kriterleri

Faz 1 kapanmadan önce şunlar sağlanmış olmalı:

- [ ] Kod tabanında `Locale::render()` dışında `switch_to_locale()` çağrısı yok
- [ ] `wp i18n make-pot` uyarısız çalışıyor
- [ ] Yer tutuculu her dizgede `translators:` yorumu var
- [ ] Admin dili `tr_TR` iken FR alıcıya kesilen fatura Fransızca üretiliyor
- [ ] XML çıktısı, UI dili ne olursa olsun bit düzeyinde aynı
- [ ] Yönetici paneli fatura üretiminden sonra hâlâ doğru dilde
